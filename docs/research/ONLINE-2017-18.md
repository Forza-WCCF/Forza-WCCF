# Online messages of 2017–18: ghosts, rankings, saves (N0, 2026-10-14)

Research for ROADMAP "Online between shops", step N0. Sources: the decrypted originals
`control_Release.exe` (Hex-Rays dump `<runtime>\ida\control.c`) and `client_Release.exe` (IDA copy
`<runtime>\ida-gamesvr2\client_Release.exe.i64`), read only. Nothing was launched. [V] = seen in code,
[A] = assumed. Addresses: `sub_` = client unless marked "control".

## Conclusions

1. **Play between shops is live, with ghost teams as the fallback** (corrected 2026-10-16). The control sends
   MATCHING_ENTRY 243 per entered seat (card id, the seat's address and outside port, entry kind, club, coach)
   and polls MATCHING_RESULT 245/246, whose answer names the opponent cabinet's address and port and a shared
   seed (control 0x4482A0 `entryMatchingInfo`, 0x448CE0 `getGetMatchingResultInfo: MatchingOK`); the opponent
   becomes seat 90 + n and the two clients talk peer to peer. The control sends this only with `GAME_SVR_ENTRY`
   set or `IS_RINGEDGE` ≠ 0 (setup writes 0). The client code alone shows only the asynchronous path:
   GHOST_MATCHING → GHOST_TEAM or BEST_ELEVEN → `REQ_MATCH` (sub_4BC150) → the shop's own match engine plays
   the stored team. Detail and plan: ROADMAP "A server of our own for 2017–18, and direct VS". [V]
2. **Inside one shop the control pairs its own satellites** (`wccf::Matching::entry`, control ~0x4782xx:
   "p2p entry (sate%d,%s,%d)"), and the clients talk peer to peer (`ClClientInterface`: ping, `TIMEOUT_P2P`,
   `P2P_DISCON`, `OPPONENT_VERSION_DIFF`, `CLIENT_PORT1..3`, `P2P_MATCHING_TEST`). Between shops the same
   peer link is set up from the game server's 246 answer (conclusion 1). The client's own server-side
   matching message, `SLS_SVR_MATCH` (sender sub_4B8540), has **no callers**: dead code. [V]
3. **No "World Trophy" network mode in 2017–18.** The network mode select (`ADV_NetModeSelect` scenes) offers
   CHALLENGE_TOUR, GRAND_TROPHY (with playoff), LEAGUE, TOURNAMENT, VERSUS / VERSUS_UC and
   UNIVERSAL CHAMPIONSHIP (area select `AreaSelect_UT`). The server-ranked tournaments are **Grand Trophy**
   (GT: weekly id, classes, points, playoff, `SERVER_COACH_GT_*`) and **Union Trophy / Universal
   Championship** (UT: area, shop and association rankings, `SERVER_COACH_UT_*`, `RNK_UnionTrophy_*`).
   World Trophy survives as save fields (`CLUB_WT_POINT`, `CLUB_WT_SUCCESSION_CHAMPION_NUM`,
   `COACH_WT_RANKING_*`, `CLUB_WT_RANKING_ENTRYFLAG`), after-game screens (`AGM_WorldTrophyPoint_*`,
   `GAM_WT_result`) and a ceremony (`537_CUP_Ceremony_Rank_WorldTrophy`). The tournament state lives on the
   server: in the save data (SAVE_DATA / SAVE_DATA_SET) and in the GMSVR_RANK answer. [V for strings; the
   WT-to-GT succession is A]
4. **Every gmsvr message is relayed by the control.** The client writes a named variable to its control link
   (vtable +4 send, +8 receive, `sub_4ADAC0(name)` = still waiting); the control (`sub_443510`, control)
   fills slot, shop id and revision 47565, sends it to the game server (TCP 20050, 40-byte header,
   `gamesvr.rs`), and copies the answer back by slot (`sub_444CC0`, control). Clients poll 150 times (about
   2.5 s) before they give up. [V]
5. **Zero answers are not all safe.** GHOST_MATCHING with zeros reads as "no opponent" and the game falls back
   to a CPU team (fine). BEST_ELEVEN and GHOST_TEAM with errCode 0 are taken as a valid team and an all-zero
   team is installed (sub_847DF0, sub_7FBB90). The stand-in should answer those two with errCode ≠ 0 until it
   holds real teams. [V for the branch; the effect of an empty team on the match is A]

## Common rules

| Rule | Detail |
|---|---|
| Request +0 | u32: client puts its satellite number (`dword_15DD9B4`); control overwrites with its slot index [V] |
| Shop id | client: `sub_4D27A0` = ALL.Net shop id parsed as hex (0 without ALL.Net); control overwrites with its own shop id (`this+74`) [V] |
| Revision | u32 47565 next to the shop id in every request [V] |
| Answer +0 | slot; the control matches answers to seats by it (stand-in echoes it) [V] |
| Answer +4 | errCode, 0 = success, for every message below [V] |
| Header status | the control uses the payload only if header status > 0 (stand-in sends 1) [V, RESEARCH.md] |

## M1: the new club and the save (2026-10-16)

Research for ROADMAP M1 ("a club survives restarts"), from the client (IDA copy
`<build-dir>\ida-m1-20261016\client_Release.exe.i64`) and the control dump. No capture of 272–292 exists.
"Error" below = the code the client shows (`err_0`+128,976 or sub_5F24D0); "timeout" = 150 polls (about 2.5 s)
unless marked 1,800.

### Ids and keys

- **Aime id** = `dword_6D9EE50`+352, the s32 from the AiMeDB lookup answer; it goes to request +4 only while the
  card is logged in (+308 set) and the login kind (+316) is not 39, else +4 = 0. [V sub_817C50, sub_817F10]
- **coachId** = save parameter at table offset 108, **cardId** = parameter at offset 104 (also copied to offset

### Stand-in answer recipe

The 3,072-byte save block is bit-packed, most significant bit first: SYSTEM_VERSION is the first 32 bits. The cpu_*.dat
files hold 0 there and the client upgrades any save below 11 through a bad address (crash at EIP 4), so the skip club
patches the version fields (bits 0, 20,736, 21,538 = 12), the ids (185, 217) and COACH_TUTORIAL_PROGRESS (bit 22,221, 6 bits, 13).

Store per (Aime id, coachId): cardId, the two names, record bytes +122 / +123, the last accepted 3,072-byte
block with its version and size, the owned-card list and an improper-end counter.

## 237/238: the client's settings block and the secretaries

Found in the first live club creation, 2026-10-16. At start-up the control asks 237 and copies the 238 answer
