# Player links ("partnerships") in 2010–11

> Research for "Links on the board" (`docs/ROADMAP.md`). Static analysis of the 2010–11 `client_Release.exe`
> (IDA, a read-only analysis copy, same size as the runtime copy; addresses below are
> that build's), the original `prog_data/player_data/*.bin` files, the original Lua event scripts under `script/`
> and a scrape of a fan card site. Nothing was launched and nothing original
> was written. No player names, records or table values from the original files appear here; counts and synthetic
> examples only. 2026-10-13.

Provenance marks: **[V]** read in the code (address given) or counted in the files. **[I]** inferred (the reason
is given). **[A]** open.

## 1. Summary

- The game keeps two different numbers for every pair of players on a club, and `partnership.bin` feeds only the
  first one. **[V]**
  - **Affinity** (the original variable names translate as "inter-player affinity value"): a fixed level **1–5** per
    pair of real players. `partnership.bin` lists 4,271 pairs with their level; every other pair gets a default
    level computed from both players' birthdays and nationalities. Affinity never shows as a line by itself.
  - **Link** (the original names translate as "player link info"; the client's own debug log calls it `Coop`): a
    growing value **0–255** per pair of squad members, saved with the club, raised by matches and by Lounge
    events. Its ceiling depends on the affinity. The lines the game draws between players are stages of the link.
- Link stages, from the Lua event scripts **[V]** and their debug titles **[I]**: no line below 150; a **thin
  white line** from 150; a **thick white line** from 200; the **golden link** at 255. Five stage boundaries at 50,
  100, 150, 200 and 253 each trigger a Lounge "stage breakthrough" event.
- For Forza-WCCF the board can show **affinity** from the player's own files alone (`partnership.bin` +
  `player_data.bin`, plus the default rule). The **link** stage needs the club save (the 120-pair arrays), which
  the board does not read yet.

## 2. `partnership.bin` layout

No header, no count, no checksum: the client reads `file size / 129` records in one go (loader `sub_4E3A80`, which
passes 129 = 0x81 both to its count helper `sub_4E3A10` and to `fread`). **[V]**

| offset | size | field | notes |
|---|---|---|---|
| 0x00 | 64 | name A | Shift-JIS (cp932) katakana full name, NUL-terminated, zero-padded; longest seen 38 bytes |
| 0x40 | 64 | name B | same encoding; the partner |
| 0x80 | 1 | level | affinity 1–5 (unsigned byte) |

- Record count 2010–11: 550,959 / 129 = **4,271**, no remainder. **[V]**
- Key: the name is the same string as `player_data.bin` record +0x177 (the second katakana full name, 64 bytes).
  The client copies record +0x177 into a `std::string` and looks it up (0x4E3F2D, 0x4E3F32). Matching is exact
  byte equality; there is no ID. **[V]**
- Direction: the loader inserts every record twice, as map[A][B] = level and map[B][A] = level (two
  nested-map inserts per record in `sub_4E3A80`, through `sub_4E44B0` and `sub_421620`), so one record covers both
  directions and the file needs no mirrored copy. **[V]**
- Order: neither sorted nor grouped (977 distinct A names spread over 2,475 runs); A and B are in no fixed byte
  order (2,219 A<B, 2,052 A>B). A reader should build its own symmetric map. **[V]**
- One record per pair; a player's partners are all records naming him on either side. There is no partner count
  field. **[V]**

Synthetic example (made-up names, not from the file): a record `"アアア・イイイ" | "ウウウ・エエエ" | 05` means
both players have affinity 5 with each other on every card of either player.

Because the key is the person's name, **all cards of the same player share his links** (793 names in
`player_data.bin` belong to more than one card record). **[V]**

## 3. How the client uses it

### 3.1 Lookup: `sub_4E3EA0(cardA, cardB)` returns 1–5 **[V]**

1. Each argument is a card number 0..0x26DF (9,951). The table at 0xAF8610 maps it to a `player_data.bin` record
   index (negative = no card); the record is base + 0x328 × index. If either card has no record the result is 1.
2. Look up record A's +0x177 name in the outer map, then record B's name in the inner map; a hit with a value ≥ 0
   is returned as is.
3. A miss falls to the default rule `sub_4E41B0`:
   - each player's birthday string at record +0x112 (`Y/M/D`, ASCII; present in all 3,927 records) goes through
     `sub_4E40D0` → `sub_4E4050`, which counts days into a 60-day cycle (month table 0xBD63C0) and maps the 60
     days onto **12 types** (table 0xAED01C, values 0–11);
   - the base level is a 12×12 table at **0xB02198** indexed by the two types (values 1–5, symmetric: all 144
     cells checked);
   - **+1** if both players have the same byte at record +0x124 (nationality: the byte splits the scraped cards by
     nationality with purity 1.00 over 54 values);
   - **−1** if either player's byte at record +0x0B is above 3 (values 1–3 cover almost all cards; 4 and 5 are a
     few dozen special cards, 5 = the "AT" series in the scrape **[I]**);
   - clamped to 1–5.
   So every pair of players has an affinity; the file only overrides the default for the pairs it lists.

A Forza-WCCF reader that wants the defaults reads the two small tables from the player's own client executable at
run time (addresses above, after checking the bytes); their values are not copied here.

### 3.2 Where it is called **[V]**

One caller: `sub_4FB4F0`, the routine that loads the 16 squad cards into the club's script variables (it also sets
age, condition type, captain, manager affinity and so on). For each squad slot i (0–15, slots 40 bytes apart, card
number a signed 16-bit word; ≤ 0 = empty) it calls `sub_4E3EA0` for every later slot j and writes the result, or 0
for an empty slot, into the variable whose name translates as **"club inter-player affinity value"** (string
0xA17D10) at pair index k (call at 0x4FBCBE, write at 0x4FBCE2).

Pair index, the same in every reader (`sub_5134B0`, `sub_4FF7C0`, `sub_5DD360`): for slots i < j,
`k = 15·i − i·(i+1)/2 + j − 1`, 0..119 (120 pairs). Slot 0 pairs are k 0–14, slot 1 pairs 15–28, and so on. **[V]**

All 16 slots take part, starters and substitutes alike; the client draws no line between position and affinity.
The squad is recomputed each time this routine runs, so affinity follows the cards on the team, not a stored
history. **[V]**

The same birthday types also give the **manager affinity** (string 0xA1FB20): the manager's type (one of 12)
against the player's type in the same 0xB02198 table (in `sub_4FB4F0`). **[V]**

### 3.3 The link value and its stages

Per-pair arrays (120 entries each), named in the client's string table:

| string | meaning (translated) | range | written by |
|---|---|---|---|
| 0xA17D10 | club inter-player affinity | 0 (empty slot), 1–5 | client `sub_4FB4F0` from `partnership.bin`; some training events push it to 1 (`sub_5249C0`, `sub_5290E0`) **[V]** |
| 0x9E34E4 | player link info ("link") | 0–255 | match results and Lounge events; zeroed for a slot whose card leaves (`sub_5DB9A0`) **[V]** |
| 0xA1C0E8 | player link evaluation | byte | copied from a server message, 120 bytes per side (`sub_4E73A0`) **[V]** |

Growth ceiling **[V]**: `sub_5DD360` raises the link and caps it at `sub_4FFCB0(affinity, current) − 1`.
`sub_4FFCB0` returns 253/200/150/100/50 for affinity 5/4/3/2/1, or the higher stage the current value already
passed (> 200, > 150, > 100, > 50). A gain is tripled when the condition variable is 5 (top condition). So affinity
decides how far a pair grows on its own: affinity 1 stalls near 50, affinity 5 can reach 253.

Stages, from `script/EventCommunication.lua` and `script/lounge/*.lua` **[V]** (the conditions) and their debug
titles **[I]** (the line names):

| link value | stage event / state | line on the Partnership screen (from the script titles) |
|---|---|---|
| < 50 | stage 1 not reached | no white line |
| = 50 / 100 / 150 / 200 / 253 at the ceiling | "link stage 1/2/3/4/5 breakthrough" Lounge events (`event009`…`event005`) lift the ceiling; stage 5 sets 254 | — |
| 51–149 | | no white line |
| 151–199 | | thin white line |
| 201–252 | | thick white line |
| 254 | "after stage 5 breakthrough, before the friendly" (`event057`); after a friendly match the client picks one 254 pair and adds 1 (`sub_47EE00`) | (thick white, **[I]**) |
| **255** | **golden link** (`event003`, `event056`); the client counts golden links and six or more unlock an achievement (`sub_6F64E0`) | **gold** |

The Lounge scripts also split affinity in two: 1–3 is "normal affinity", 4–5 "best affinity" (`event014` vs
`event015` and the same pattern in each group). **[V]**

### 3.4 Match and control servers

`match_Release.exe` and `control_Release.exe` also open `prog_data/player_data/partnership.bin` and carry the same
120-pair names plus a per-pair "link change value", a "link coefficient total" and a coach report for "just before
golden link". The match engine is where the link grows and where links affect play; that code was not read. **[V]**
(strings) **[A]** (behaviour)

## 5. Verification (counts only)

Script `verify.py` in the session scratch folder (not committed), Linux `python3 -I`, read-only.

| check | result |
|---|---|
| size / 129 | 4,271 records, remainder 0 |
| padding after each name | all zero in every record |
| names decode as cp932 | 4,271 of 4,271 |
| levels | 1: 137, 2: 238, 3: 784, 4: 1,746, 5: 1,366; nothing outside 1–5 |
| self-pairs | 0 |
| unordered pairs | 4,263; 8 pairs listed twice, all with the same level |
| distinct names | 1,212; **1,181 resolve** to a `player_data.bin` +0x177 key, **31 do not** (players without a 2010–11 card, **[I]**) |
| players with any listed partner | 1,181 of 1,663 distinct keys |
| partners per listed player | min 1, median 4, mean 7.05, max 57 |
| `player_data.bin` | 3,927 records of 0x328, no header; every birthday field parses as `Y/M/D` |
| card-site ◎ marks (10-11 and 10-11 V2.0 pages, names matched) | in the file: level 5 × 634, level 4 × 14, level 1 × 2; absent from the file 193; unmatched names 371 |
| card-site × marks | in the file: level 1 × 17, level 2 × 19, level 3 × 2, level 4 × 8, level 5 × 3; absent 44; unmatched 22 |

Read: the site's ◎ is level 5 (97 % of the matched pairs), × is mostly levels 1–2; "absent" pairs fall to the
birthday default, which the check did not compute. Name matching folded `＝`/`=` to `・` and dropped spaces only, so
the unmatched counts are a matching limit, not a decode error.

## 8. The link array in the club card (2026-10-15)

Settled from the club card schema (`legacy/2010-11/code/cards/schema.py`, the client's own field tables) and checked
against a real club card (counts only). **[V]**

- Field: Club group, `CLUB_PLAYER_COOPERATION_INFO` (選手連携情報, "player link info", the 0x9E34E4 variable of
  section 3.3), 120 × 8 bits. With the groups' byte padding (section 3 of `CLUB-CARD-2010-11.md`) it starts at
  **payload bit 3650** (byte 456, bit 2: not byte-aligned), MSB-first like every card field; entry k = bits
  3650 + 8k. The 4-bit `CLUB_COOPERATION_OPINION` (選手連携評価, "link evaluation") follows at bit 4632.
- Pair order: entry k is slots i < j by `k = 15·i − i·(i+1)/2 + j − 1` (section 3.2).
- Slots: slot i is `Player[i]` of the card (payload bit 6688 + 312·i), its card number `PLAYER_CARD_NO` (14 bits).
  The board does not need the table's order: a board card is matched to its slot by card number
  (`fpr_table0.txt` lists card numbers; on that card all 16 table cards are the club's 16).
- Read from the copy the game reads: copy A when its checksum is good, else copy B (section 4 of the club card doc).
- Check on that card: 16 filled slots; values 0–199 (107 pairs below 150, 13 thin, no thick or gold yet);
  no value on a pair with an empty slot. Every pair's link stays at or under its affinity's ceiling (affinity
  5/4/3/2/1 → 253/200/150/100/50, section 3.3) with this order and the default rule of section 3.1 (0 of 120 over);
  the same check with the slots reversed puts 24 pairs over. That confirms the offset, the pair order, the slot
  mapping and the default rule together.

The default rule's month table (0xBD63C0) is the standard days-before-month count from March, `(153·n + 2) / 5`, so
a reader computes it; only the two tables (60 types at 0xAED01C, file offset 0x6EB21C; 12×12 levels at 0xB02198,
file offset 0x700398) come from the player's own client program, checked by shape (types 0–11, levels 1–5,
symmetric) before use. Seat 1's runtime copy holds the same bytes there. `sub_4E40D0` passes
month in eax, year in ecx and day on the stack to `sub_4E4050` (disassembly at 0x4E412B).

Reader: `forza::cards::links` (`Affinity`, `ClubLinks`); its ignored test `the_players_own_files` repeats the
ceiling check on the player's own files and prints counts only.

### 2017–18

`partnership.bin` there: 704,340 bytes = **5,460** records of 129, remainder 0; all names zero-padded; levels
1: 168, 2: 270, 3: 788, 4: 2,047, 5: 2,187. **[V]** Its `player_data.bin` has 8,434 records of 0x620; the 2010–11
fields sit from +0x288 (the catalogue maker's `cards1718.py`), so the key is +0x41F: 1,769 of the file's 1,810
names resolve to a record (+0x2F0, the first katakana name, gives 1,737). **[V]** The 2017–18 client holds both
default tables byte for byte (file offsets 0x11B4494 and 0x11BFC50) **[V]**, so the same default rule very likely
holds **[I]**; the reader uses listed pairs only for 2017–18 until the rule is read in that client. The 2017–18 club
card's link array is not located: the board draws no lines for 2017–18 and logs it. **[A]**
