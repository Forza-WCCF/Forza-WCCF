# Online messages of 2010–11: game server, matching between shops, World Trophy (N0, 2026-10-14)

Research for ROADMAP "Online between shops", step N0, the 2010–11 part. Sources: the original
`control_Release.exe` and `client_Release.exe` from `ringedge/revd-continuation/extracted/` (read only), analysed
on copies in `<build-dir>\ida-online-1011-20261014\` (new control IDB; the client IDB is the cached full
analysis of the same hash). `match_Release.exe` was only string-searched. Nothing was launched, nothing was sent.
[V] = seen in code, [A] = assumed. Addresses: control unless marked "client".

## Conclusions

1. **The control program is the only one that talks to the publisher's service.** It opens one TCP link to the
   game server ("gmsvr") at `GAME_SVR_IP:GAME_SVR_PORT` (an address other than `127.0.0.1` overrides the one
   ALL.Net gives; `connectCtrl` sub_43C430) and frames every message with **the same 40-byte header as 2017–18**
   (magic `F1 C0 80 44 B4 9E DA 3C`, u16 command, u16 sequence, u32 status, u32 total size, u32 connection id,
   u8 checksum at +24, 15-character text at +25; builder sub_408650, check sub_4088C0). Clients and match engines
   never reach it; they ask their own control. [V]
2. **Today nothing answers, and the control does not even dial.** It connects only when ALL.Net authentication
   succeeded (sub_49B750 = 1); the kit writes `ALLNET_AUTH=0` and `GAME_SVR_IP=127.0.0.1` and starts no game server
   stand-in for 2010–11 (`crates/launcher/src/run/mod.rs:1203`, 2017–18 only). The 2010–11 stand-ins on TCP
   40100–40107 (`standins/network.rs`) answer only the keychip/master/amNetwork text protocol. TCP 20050 on a
   2010–11 server is the log inbox (`crates/server/src/inbox.rs`), a different protocol. So every online feature
   is off: the control logs "logoff", WT stays closed, every seat plays its own shop. [V]
3. **2010–11 has live matches between shops, brokered by the game server and played peer to peer over UDP.**
   The control sends each network-entered seat to the server (ENTRY_MATCHING 243: card id, the seat's public
   IP and NAT outside port, club and coach names, entry kind) and polls MATCHING_RESULT 245, whose answer carries
   **the opponent cabinet's IP and port, club, coach and shop name and a shared random seed** (sub_440230,
   sub_456A60). The opponent becomes a seat id 90–99, and the control hands the client `ENEMY_INFO` with that
   address exactly as for a local seat (sub_42EE20); the client opens a `DatagramSocket` P2P link to it
   (client sub_408230 → sub_447020 → sub_447100), local seats on 20000 + seat, a host also on 20020. NAT
   traversal uses a **reflect server** whose address the login answer gives (`RFSVR_INFO` to every client,
   sub_433720; client sub_409440 learns its outside address); the outside port returns in `ENTRY SVR` and goes to
   the server in ENTRY_MATCHING (sub_42B4C0 → `UserData::setOutsidePort`). [V]
4. **The World Trophy is one of those live network modes, open in a daily time window.** The server-info answer
   holds a WT window (u16 start, u16 end, HHMM up to 4800 for after midnight; `checkWTOpen` sub_4473F0). While it is
   open the controller runs `GameManage::wtMatching` (state 4, sub_44ED20) and seats flagged for WT enter matching
   with kind 3 (sub_45C3F0). Unmatched entries fall back to a CPU team (`recv:%d,omit:%d`, sub_456A60), and the
   control can also field a "ghost" (an opponent rebuilt from stored data, `ghost%d Away -> sate%d Home`,
   `isGhost`); where ghost data comes from is [A]. WT points go up with the club's play report (PLAY_RESULT_WT
   241, three WT values); rankings come down in WT_RANKING 252 and GMSVR_RANK 250. [V for the paths, A for
   point rules]
5. **There is an asynchronous mode as well: DATA VS.** `entryDataBattleInfo` (257, a 4,556-byte team upload),
   DATA VS rankings (259 → 12,216 bytes) and live/replay data (261 → 1,024 bytes; `VtrPlayData`, `LiveGameInit`)
   match the 2017–18 ghost pattern: the server keeps teams and results and the cabinet replays them. [V for the
   messages, A for the semantics]
6. **The protocol is the direct ancestor of the 2017–18 one.** Same framing, the same message numbers in the
   same 200–300 range, several identical answer sizes (226 = 260, 228 = 12, 234 = 1,092, 240 = 12, 244 = 12),
   GMSVR_RANK 249/250 and GMSVR_ECHO 18 by name. `standins/gamesvr.rs` can serve 2010–11 with a second size
   table. [V]

## Common rules

| Rule | Detail |
|---|---|
| Header | 40 bytes, as `gamesvr.rs` `header()`; status (+12) = 1 when the sender waits for an answer, 0 for one-way [V] |
| Answer id | request id + 1; the control registers the answer buffer, its size and the slot before sending (sub_406E20) [V] |
| Ids < 100 | handled by the link layer itself: 2 (ping, answered with 2), 15, 18 (echo), 43–55 odd (acknowledges of the one-way logs 44–54) (sub_407450) [V] |
| Ids 100–500 | go to the game-server handler; payload length must fit the received size [V] |
| Header text | the cabinet's main id (`myIdStr`), or "PC" in a non-RingEdge build (sub_43CCE0) [V] |
| Online gate | every request checks the control's online flag (+232, set by the login answer) or a forced-online option (`FORCE_ONLINE`) [V] |
| Shop id | from ALL.Net (sub_4167D0), written into requests that carry it [V] |

## Login 201 → 202

Request, 20 bytes: +0 u32 0, +4 u32 7128 (the cabinet revision), +8 u32 shop id, +12 char[4] (region text,
sub_416860), +16 u8 a flag from the network-settings object. [V]
Answer: the control reads +8 u32 IP and +12 u16 port of the **reflect server** and passes them to every client as
`RFSVR_INFO` (16-character IP + u16 port); a non-empty answer sets the online flag ("login !"). +0/+4 (myId)
[A]. Zero answer: online with no reflect server; clients then cannot learn their outside port. [V for the read]

## World Trophy

- **Open or closed**: server info +36/+38 (above). `FORCE_WT` exists as a control option [V string, A effect].
- **Entry**: seats flagged for WT (+654) enter with kind 3 only while WT is open; the WT cycle is controller
  state 4 (sub_44DF90 → sub_44ED20), with its own table `wtMatch_tbl` (sub_42EE20). [V]
- **Points up**: the client's end-of-play `TEAM DATA RSLT` carries a WT flag and three values; the control then
  sends 241 instead of 239 (sub_42BA90 → sub_43EE50, log `wt=(%d,%d,%d)`), followed by the card payload 209.
  241 = the 292-byte club header (card id, coach id, a 16-byte id stored byte-reversed at +12/+20, coach name
  +24, club name +80, shop id +140, packed record +160, 16 × player id and two bytes +164), then the three WT
  values and a fourth +292, 128 bytes, the payload size +436 and the 1,676-byte club payload +440. [V layout, A
  which WT fields; per `CLUB-CARD-2010-11.md` §5.4 they are the four WT point fields]
- **The sent mark**: `USER_WT_POINT_TRANSMISSION_FLAG` is cleared when the cabinet sees an accepted `NETWORK_ID`
  (CLUB-CARD §5.2). The control answers some reports itself with a local `NETWORK_ID` (sub_42BA90, 28 bytes, ids
  −1); which server answer produces the accepted one (228 or 240/242) is [A].
- **Rankings down**: WT_RANKING 252 (5,548 bytes) is copied whole to control +3528 and served to the projector
  and clients as `REQ_RNK_WTA_INF` / `WTJ` / `WTT` (area, Japan, top) [V names, A split]. Its log names +0 and +4
  (period from → to), the champion at +8 (char[28]), +36 (char[56]), +92 (char[56]), and +148/+152/+156 [V
  offsets, A meaning]. GMSVR_RANK 250 (316 bytes) gives each card its WT standing: +8 CS rank, +12/+16 current WT
  rank (two values), +20/+24 last week's, +28 s16 WT week, +30..+39 rankIn (s8, u16, u16 twice), +40 s16 DATA VS
  week, +42 jwc, +43 ac, +46 wwc, +47 asia results, +60 and +188 social-network tokens (leave empty) (sub_43E3F0).
  Request 249, 32 bytes: +4 card id, +8 coach id, +20 s16 weekChkPM, +22 s16 weekChkWT, +29 u8 online. [V]
- **Screens**: client `AGM_WorldTrophyPoint_*` (after-game points, entry or no entry), `GAM_WT_result`,
  `MNG_Coach_WorldTrophyRankingData_*` (coach data), competition icon `0809_KUM_CompetitionIcon_64_WT`; engine
  `467–469_ENT_WorldTrophy`, `537_CUP_Ceremony_Rank_WorldTrophy`, `jingle_15_world_trophy`. [V strings]
- **Penalty**: the 5,000 WT points per fifth improper end come from server info +28. [V]

## Traffic between cabinets

| Link | Who | Transport | |
|---|---|---|---|
| Seat ↔ own control | every client | TCP `CONTROL_PORT` 20002 | V |
| Seat ↔ match engine | client ↔ `match_Release` | `MATCH_PORT` 20003, `CLIENT_PORT1..3` | V strings |
| Seat ↔ seat, same shop | clients | UDP, 20000 + seat; host also 20020 | V |
| Seat ↔ seat, **other shop** | clients, opponent ids 90–99 | UDP to the address from 246; NAT outside port from the reflect server; a peer outside 192.168.x sets the remote mode | V |
| Control ↔ game server | control | TCP `GAME_SVR_IP:GAME_SVR_PORT` | V |

Forza-WCCF already relays seat-to-seat UDP inside a shop (`forza-server` relay, UDP 20040, `relay.rs`); a match
between shops needs the same relay reachable from both shops, since a hub cannot rely on hole punching.

## What the hub must answer

1. **Login 201/202**: online flag, reflect server address (the hub's or a relay's). Without it nothing else runs.
2. **Server info 269/270**: clock, the 844-byte game-control block with the penalty defaults, and the **WT window**.
   Zeros close WT and zero the penalties.
3. **Matching 223/224, 243/244, 245/246**: a sequence id; accept entries; pair entries of the same kind across
   shops (kind 3 = World Trophy); return each side the other's address (rewritten to the relay), names, a shared
   seed and who is home. "No match" is a safe default.
4. **Play reports 239/240, 241/242, 209/210**: store the club payload and WT values, update WT points and ranks;
   answer accepted so the cabinet clears its unsent counters (exact clearing answer: Open).
5. **Rankings 233/234, 251/252, 249/250, 259/260**: team, WT and per-card standings; zeros are safe.
6. **Card-in 227/228**: issue or confirm the club's network id; must never contradict the card (CLUB-CARD §9.6).
7. Local only, not the hub: echo 18, telop 225/226 (empty), CPU data 263/267, usage 265, bad players 255, one-way
   logs 44–52 and 235 (drop), DATA VS until decoded (errors or zeros).
